Why Workers AI is here — and why it is not the coding model

Three jobs, all plumbing

  • • Embeddings. @cf/baai/bge-base-en-v1.5 at memory-do.ts:412. Batched, 768-dim, feeds Vectorize. Runs inside the DO with no key and no egress.
  • • Session distillation. @cf/zai-org/glm-4.7-flash at session-distill.ts:259. Compresses a finished run into bankable facts.
  • • Automation gate. automations-do.ts:90. The run_when fuzzy gate falls back to Workers AI when TYPESAFE_API_KEY is unset.

Why not route these through AI Gateway?

  • • No credential to leak. The AI binding needs no key. The container path needs a key, an allowlist entry, and a handler.
  • • No egress interception. Embeddings never touch your deny-by-default allowlist, so there is no handler to write and no scope to get wrong.
  • • Latency. An in-DO call beats a Worker → gateway → provider round trip for a 768-dim vector.
  • • It is a fallback, not a dependency. Delete the AI binding and you lose embeddings, distillation, and the keyless automation gate. Nothing else breaks.

What it must never do

  • • Never write code. Coding goes through the container harness and AI Gateway. Workers AI has no repo, no egress allowlist, and no approval gate.
  • • Never hold a provider key. The point of egress.ts is that the real credential attaches at the boundary. A binding that authenticates for you removes that control.
  • • Cost trap: session-distill runs on every completed run. With MEMORY_ENABLED on, that is one extra model call per run, forever.
  • • Fine as-is: embeddings are cheap and batched. Distillation is the one to watch.
The rest of the system

The moat: approval gate + egress

  • • delegate_coding_task carries needsApproval. The route is frozen before a run id is minted.
  • • Rejection starts zero containers, not a cancelled one.
  • • egress.ts is deny-by-default. Real key attaches at cf-aig-authorization; the container only ever sees a dummy.
  • • approveRepoScope() narrows GitHub to one /owner/repo for one run.
  • • Subscription harnesses are opt-in and dark. If multi-tenancy lands, they are removed, not reworked.

Execution spine

  • • 9 Durable Objects are the only authoritative state. D1, KV, R2, Vectorize only support.
  • • CodingOrchestrator plans and delegates. It never edits a repository itself.
  • • Runs survive client disconnect via schedule() alarms + reclaimRuns, not sleeps.
  • • Harness seam: configFile, buildArgv, parseEvent, capabilities, verify.
